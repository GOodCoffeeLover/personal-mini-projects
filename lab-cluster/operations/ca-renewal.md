# Продление трёх CA `lab-cluster` примерно до 2126 года

Статус: согласованный план; продление сертификатов ещё не выполнено. Результаты
предварительной проверки относятся к обсуждению 24–25 октября 2026 года. Перед
применением повторить проверки исходного состояния.

## 1. Результат и выбранный подход

Подготовить и выполнить пошаговый runbook для существующего кластера
`10.60.80.1:6443`. Перевыпустить три корневых сертификата с сохранением текущих
ключей, затем обновить все действующие копии доверия. Краткие перерывы сервисов
допустимы; одновременно выводить из работы больше одного control-plane узла нельзя.

| CA | CAPI Secret в namespace `lab-cluster` | Файл на каждом узле |
| --- | --- | --- |
| Kubernetes | `lab-cluster-ca` | `/etc/kubernetes/pki/ca.crt` |
| etcd | `lab-cluster-etcd` | `/etc/kubernetes/pki/etcd/ca.crt` |
| front-proxy | `lab-cluster-proxy` | `/etc/kubernetes/pki/front-proxy-ca.crt` |

Во время предварительной проверки все три CA истекали 21 октября 2036 года в
16:03:03 UTC. Их соответствие CAPI Secrets подтверждено непосредственно на
`10.60.80.102`; прямую проверку на `.101` и `.103` необходимо завершить после
подтверждения SSH host keys.

Зафиксировать следующие решения:

- Срок — **36 500 суток от единого момента подготовки**, около 100 лет. Это
  соответствует максимуму поля срока CA в установленной CRD CAPI.
- Сохранить приватные ключи, Subject/Issuer, serial, исходный `notBefore` и все
  X.509 extensions. Изменяются `notAfter` и подпись сертификата.
- Существующие годовые сертификаты компонентов не перевыпускать в рамках этой
  операции.
- Ключи ServiceAccount, CA Cilium/Hubble и сертификаты webhook оставить без
  изменений.
- Cluster, Machines, Nodes и состав etcd сохранить. Шаблоны CAPI, версии
  компонентов и параметры rollout не менять.
- Для текущего кластера не устанавливать
  `caCertificateValidityPeriodDays: 36500`: поле относится к генерации CA,
  объявлено неизменяемым и не продлевает существующие сертификаты.
  [Справочник CAPI](https://cluster-api.sigs.k8s.io/reference/api/crd-api-reference.html).

Метод перевыпуска уже проверен на временных тестовых сертификатах: сохранение
идентичности и расширений, проверка старых и новых leaf-сертификатов обоими
вариантами CA, проверка нового CA на дату в 2100 году. Перед применением те же
проверки выполнить для реальных сертификатов кластера.

## 2. Подготовка, условия допуска и резервные копии

### Шаг 1. Восстановить проверенный SSH-доступ ко всем узлам

На `.101` и `.103` во время предварительной проверки обнаружено несовпадение SSH
host keys. Сверить новые отпечатки с локальными консолями соответствующих машин,
затем адресно обновить записи `known_hosts`. Сохранить
`StrictHostKeyChecking=yes`.

До подтверждения доступа с `sudo -n` ко всем трём узлам изменения сертификатов
не начинать.

| Узел | Адрес |
| --- | --- |
| `asus-pn41-1` | `10.60.80.101` |
| `asus-pn41-2` | `10.60.80.102` |
| `beelink-1` | `10.60.80.103` |

### Шаг 2. Повторить проверку исходного состояния

- Использовать только `lab-cluster/.state/lab-cluster.kubeconfig`. Корневой файл
  `lab-cluster.kubeconf` относится к другому кластеру на `192.168.1.5`.
- Для запросов к лабе исключить её адреса из HTTP-проксирования через `NO_PROXY`.
- Подтвердить три Ready Node, три исправных etcd member, отсутствие alarms и
  операций создания, удаления или замены Machines.
- Проверить `/readyz?verbose` через VIP и напрямую через каждый control-plane IP;
  подготовить отдельные аварийные kubeconfig с прямыми адресами.
- На всех узлах сравнить три CA с соответствующими CAPI Secrets по SHA-256
  сертификата. Проверить соответствие сертификатов приватным ключам, выводя
  только отпечатки публичных ключей.
- Зафиксировать UID Cluster, Machines и Nodes, member IDs etcd, владельца VIP,
  размещение Pod и состояние приложений.
- Записать исходные отпечатки leaf-сертификатов, чтобы обнаружить
  непредусмотренный перевыпуск.

Любое несовпадение CA между узлами и Secrets или неисправность исходного кластера —
условие остановки до выяснения причины.

### Шаг 3. Создать защищённый комплект восстановления

Использовать отдельный каталог
`lab-cluster/.state/ca-renewal/<UTC-время>/`: права каталога `0700`, секретных
файлов `0600`, `umask 077`. Проверить, что каталог исключён из Git.

Сохранить:

- Три CA Secrets, `lab-cluster-kubeconfig`, ресурсы Cluster/KCP/Machines и их
  исходные настройки паузы.
- С каждого узла — `/etc/kubernetes`, конфигурацию kubelet, его PKI и контрольные
  суммы файлов.
- Локальный kubeconfig, `cluster-info`, `extension-apiserver-authentication`,
  действующие копии CA в ConfigMaps и найденных Secret.
- Отчёт инвентаризации с привязкой каждого сертификата к роли и месту хранения.

Резервные копии static Pod manifests хранить **за пределами**
`/etc/kubernetes/manifests`, чтобы kubelet не прочитал их как дополнительные
манифесты.

Подготовить `etcdctl` и `etcdutl` **3.7.0** из официального релиза, проверить
опубликованные контрольные суммы. Во время предварительной проверки серверы etcd
имели версию 3.7.0, установленный на `.102` клиент — 3.5.16. Если версии серверов
к началу работ изменились, сначала актуализировать план резервирования.

Снять snapshot с одного исправного endpoint, проверить
`etcdutl snapshot status` и выполнить пробное восстановление в отдельный временный
каталог без запуска восстановленного member. Скопировать snapshot и резервные
копии узлов на рабочую машину.
[Резервирование и восстановление etcd](https://etcd.io/docs/v3.7/op-guide/recovery/).

### Шаг 4. Приостановить управление жизненным циклом машин

- Установить `Cluster.spec.paused: true`, дождаться подтверждения паузы CAPI.
- Убедиться, что текущие операции с Machines завершены.
- На время работ исключить ручной Sync `lab-cluster-cluster` и изменения
  инфраструктурной конфигурации.
- Контроллеры, API и admission webhooks оставить работающими.

Snapshot должен быть получен до установки паузы, чтобы аварийная копия содержала
исходное состояние управления.

## 3. Подготовка новых CA и проверка совместимости

### Шаг 5. Сформировать три новых сертификата вне рабочих каталогов узлов

Исходниками считать сохранённые CAPI Secrets, совпавшие с сертификатами на всех
узлах. Для каждого CA использовать именно его существующий приватный ключ.

Зафиксировать один `TARGET_NOT_AFTER`: момент подготовки плюс 36 500 суток.
Исходный `notBefore` каждого сертификата преобразовать в ASN.1 UTC-формат.
Перевыпуск выполнять локальным OpenSSL 3.6.4 по схеме:

```bash
openssl x509 \
  -in old.crt \
  -signkey old.key \
  -sha256 \
  -not_before "$OLD_NOT_BEFORE" \
  -not_after "$TARGET_NOT_AFTER" \
  -out new.crt
```

Это схема команды для одного CA, а не готовая команда для рабочего каталога.
`old.crt`, `old.key` и `new.crt` обозначают отдельные файлы соответствующей роли
в защищённом комплекте подготовки. Обе даты передаются в UTC в формате
`YYYYMMDDHHMMSSZ`; дату окончания нужно зафиксировать один раз для всех трёх CA.

Преобразование существующего сертификата сохраняет расширения, если не указан
`-clrext`; сохранность всё равно проверить явно.
[Документация OpenSSL](https://docs.openssl.org/3.5/man1/openssl-x509/).

У всех трёх текущих CA одинаковый `CN=kubernetes` и serial `0`. Поэтому
сопоставлять их только по роли, старому отпечатку и публичному ключу.

### Шаг 6. Проверить каждый результат до первого изменения в кластере

- Сохранены Subject, Issuer, serial, `notBefore`, публичный ключ и полный набор
  расширений.
- Сохранены `CA:TRUE`, `pathlen:0`, Key Usage и Subject Key Identifier.
- Самоподпись корректна; срок соответствует зафиксированному
  `TARGET_NOT_AFTER`.
- SHA-256 сертификата изменился; SHA-256 публичного ключа остался прежним.
- Существующие leaf-сертификаты со всех узлов проверяются соответствующим новым
  CA: API, kubelet client, встроенные сертификаты kubeconfig, etcd
  server/peer/client и front-proxy client.
- Временный kubeconfig с новым Kubernetes CA успешно обращается к VIP и ко всем
  трём API endpoint.
- Проверка нового CA на дату в 2100 году проходит. Истёкший к тому времени
  годовой leaf для этой проверки не использовать.

При любой ошибке применение не начинать. Не заменять сохранение ключей
генерацией новых ключей как обходным решением.

## 4. Применение и распространение доверия

### Шаг 7. Обновить источник сертификатов в CAPI

Адресно заменить только `data["tls.crt"]` в трёх CA Secrets. Использовать проверку
исходного значения и `resourceVersion`, чтобы не затереть параллельное изменение.

Сохранить `tls.key`, тип Secret, labels и ownerReferences. После каждого
изменения перечитать Secret и сверить отпечатки сертификата и публичного ключа.

Secrets не удалять и не пересоздавать: CAPI использует существующие пары
сертификат/ключ при подготовке bootstrap.
[Логика хранения сертификатов CAPI](https://github.com/kubernetes-sigs/cluster-api/blob/main/util/secret/certificates.go).

### Шаг 8. Обновить узлы последовательно: `.102` → `.101` → `.103`

На каждом узле полностью закончить следующие действия до перехода к следующему:

1. Подготовить файлы рядом с целевыми, проверить отпечатки и атомарно заменить
   три `.crt`, сохранив владельца и права. `.key` не изменять.
2. В существующих `admin.conf`, `controller-manager.conf`, `scheduler.conf`,
   `kubelet.conf`, а также обнаруженных bootstrap/super-admin kubeconfig заменить
   только соответствующий CA. Сохранить адреса серверов, credentials и ссылки
   на ротируемые сертификаты kubelet.
3. Через SSH последовательно перезапустить контейнеры static Pods: etcd,
   kube-apiserver, kube-controller-manager, kube-scheduler, kube-vip. Использовать
   `crictl stop` для конкретного текущего контейнера и дождаться его пересоздания
   kubelet. После каждого компонента проверить восстановление работы.
4. Перезапустить kubelet и проверить его подключение к API.

Удаление mirror Pod через Kubernetes API не использовать как способ перезапуска
static Pod. Перезапуск kubelet сам по себе также не заменяет перезапуск
контейнеров.

**Условие перехода к следующему узлу:** все три etcd endpoint исправны, нет
alarms, локальный API и VIP отвечают, Node Ready, static Pods готовы, новых
TLS-ошибок нет. На восстановление компонента отвести до пяти минут, затем
остановить продвижение и откатить текущий узел.

### Шаг 9. Обновить остальные действующие копии CA

После завершения всех трёх узлов:

- Заменить Kubernetes CA в `lab-cluster-kubeconfig` и рабочем внешнем kubeconfig,
  сохранив клиентские сертификаты и ключи. Отдельно проверить доступ обоими
  kubeconfig.
- Обновить CA во встроенном kubeconfig `kube-public/cluster-info`; дождаться
  обновления JWS для действующих bootstrap tokens. Discovery pin публичного
  ключа должен остаться прежним.
- Дождаться публикации нового CA в `kube-root-ca.crt` каждого namespace
  работающим controller-manager.
- Проверить `extension-apiserver-authentication`: поля `client-ca-file` и
  `requestheader-client-ca-file` должны содержать соответствующие новые CA.
  После обновления всех API servers адресно удалить старые версии сертификатов
  из этих полей, сохранив прочие данные и посторонние CA. Убедиться, что старые
  версии не появляются повторно.
- При наличии старых ServiceAccount token Secrets обновить только содержащуюся
  в них копию CA.
- Повторно проверить webhook, conversion-webhook и APIService bundles. Во время
  предварительной проверки совпадений с тремя кластерными CA не было;
  независимые сертификаты этих компонентов сохранять.

В файлах, используемых для подписи, оставить по одному соответствующему CA.
Не превращать `--cluster-signing-cert-file` в bundle.

Старые сертификаты в уже использованных bootstrap Secrets и cloud-init архивных
файлах учитывать как исторические данные: не редактировать и не использовать
повторно для provisioning.

### Шаг 10. Перечитать доверие в работающих приложениях

Дождаться обновления смонтированных CA, затем последовательно пересоздать Pod
потребителей in-cluster API:

- Cilium agents — строго по одному, затем Cilium operator.
- CoreDNS — по одному Pod.
- cert-manager и его контроллеры.
- CAPI Operator и пять CAPI providers.
- Компоненты Argo CD.
- `home-vpn`.

После каждого компонента ждать готовности и проверять связь с API.
Пересоздавать Pod через их существующие контроллеры; не менять шаблоны workloads
посредством `rollout restart`, чтобы Argo self-heal не запускал дополнительное
обновление. Самостоятельные Pod без контроллера предварительно фиксировать и
восстанавливать из сохранённого определения.

## 5. Приёмка, откат и документация

### Критерии успеха

- На всех узлах, в трёх CAPI Secrets и во всех действующих копиях доверия
  установлены согласованные новые CA.
- Все три CA имеют целевой срок; публичные ключи сохранены.
- Cluster, Machines, Nodes и etcd member IDs не изменились.
- Три узла Ready, etcd без alarms, все API endpoint и VIP исправны.
- Работают DNS, связь Pod между узлами, Argo CD и `home-vpn`; в логах нет новых
  ошибок проверки сертификатов.
- Старые отпечатки встречаются только в резервных копиях и явно учтённых
  исторических bootstrap-данных.

Затем восстановить исходное значение `Cluster.spec.paused`, дождаться здоровых
условий CAPI и проверить отсутствие незапланированного rollout. Наблюдать кластер
минимум десять минут, включая повторную проверку сертификатов в Secrets и
ConfigMaps.

### Откат

- До изменения Secrets — прекратить операцию; рабочий кластер ещё не изменён,
  кроме установленной паузы. Если продолжение работ отменено и исходное
  состояние исправно, восстановить исходное значение паузы.
- При проблеме на узле — оставить CAPI на паузе, восстановить его прежние CA и
  kubeconfig, повторить последовательные перезапуски и проверки. Следующий
  узел не трогать.
- При отказе от всей операции — вернуть исходные CA на уже обработанных узлах
  по одному, восстановить данные трёх Secrets, kubeconfig и опубликованные
  копии доверия. После полной проверки снять паузу, восстановив её исходное
  значение.
- Не восстанавливать snapshot etcd как обычный откат сертификатов: это
  откатывает также данные кластера. Snapshot использовать только для отдельной
  аварийной процедуры при невозможности восстановить существующий etcd.

### Артефакты выполнения

- На этапе подготовки выполнения дополнить этот runbook точными командами для
  зафиксированного состояния, ожидаемыми результатами и журналом прохождения
  этапов. Приведённая выше схема перевыпуска не заменяет проверки допуска.
- В README и PLAN зафиксировать фактические сроки, способ перевыпуска и
  расположение защищённых резервных копий.
- Документировать отдельно: для нового кластера срок задаётся до первой
  генерации через `caCertificateValidityPeriodDays: 36500`. Рабочий шаблон
  существующего кластера в этой операции не менять.
- В Git сохранять только инструкции и отчёт без секретных данных. Приватные
  ключи, kubeconfig и snapshots оставить в защищённом комплекте восстановления.
